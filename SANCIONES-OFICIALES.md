# Sanciones oficiales de todas las categorías

La pestaña Sanciones y los avisos del próximo rival/plantilla leen `/api/private/sanctions`, no calculan suspensiones a partir de una tarjeta. La fuente es la consulta de sanciones de la intranet federativa, temporada 22 (2026/27), para las 17 categorías incluidas en teams.json (16 grupos distintos). Lee las resoluciones de acumulación, doble amonestación y otras suspensiones con duración publicada, incluidas las del cuerpo técnico.

El endpoint verifica sesión Firebase y administrador o entrenador aprobado con el equipo asignado. La consulta privada no pasa por la caché pública y sus datos no entran en Git, en el paquete público de la APK ni en endpoints de la afición. El dispositivo conserva una copia por cuenta, equipo y alcance; si falla la red mantiene la copia anterior y advierte del fallo. El endpoint público anterior conserva únicamente sus datos derivados de actas públicas.

`official-sanctions.cjs` interpreta la página ISO-8859-1/Windows-1252: filtros de temporada/competición/grupo, cabeceras de jornada generadas con document.write, identificadores federativos, jugadores y técnicos. Una página vacía, de login o de otro grupo se considera un fallo, nunca ausencia de sanciones. Se conservan solo las suspensiones con duración y las amonestaciones necesarias del club para sus avisos; no se exportan perfiles, documentos personales, contactos ni datos de acceso del portal.

Los partidos restantes se estiman contando partidos jugados posteriores del mismo equipo en esa competición; no se suman partidos de otros equipos. La duración publicada se conserva por separado. En sanciones por tiempo, si no se publica el comienzo, no se inventa una caducidad: se indica inicio y vigencia por comprobar. Cumplimiento, fecha de inicio real, cambios de equipo y resoluciones posteriores pueden exigir revisar el original. La pantalla mantiene el enlace oficial y la indicación de estimación; no convierte automáticamente una tarjeta ni un aviso de amarillas en una suspensión.

`official-sanctions-schema.sql` crea de forma aditiva las tablas privadas de VISITS_DB. `scripts/sync-official-sanctions.cjs --publish`, ejecutado con NODE_USE_ENV_PROXY=1 en el entorno, usa RFFM_USERNAME y RFFM_PASSWORD únicamente contra intranet.ffmadrid.es. Valida el acceso, descarga los grupos autorizados, guarda los registros filtrados en D1 y entrega una sesión de consulta como secreto RFFM_SESSION del Worker. No imprime ni guarda las contraseñas o cookies en archivos, argumentos públicos, APK, Git o variables EXPO_PUBLIC. Las credenciales ya configuradas en el entorno permiten volver a conectar cuando haga falta. No se requiere activar facturación.

El cron existente revisa un grupo por ejecución: resolución horaria jueves y viernes, cada seis horas los demás días, y una consulta ligera del formulario para mantener la sesión cada diez minutos cuando no hay grupos pendientes. Una sesión nueva se comprueba en la primera ejecución. La intranet puede invalidar la sesión por expiración, cierre o cambios propios: no se promete vigencia indefinida. Se conservan siempre las últimas resoluciones correctas, se marca la conexión caducada y se puede renovar ejecutando el script con las credenciales privadas. No se almacenan contraseñas federativas en el Worker. La cola usa una exclusión temporal para no duplicar cron concurrentes; las actualizaciones de grupo no pueden pisar respuestas iniciadas más recientemente.

Preparación y publicación: aplicar el esquema, ejecutar la sincronización privada, validar pruebas, preparar únicamente los datos públicos de la versión con npm run prepare:release-data y npm run check:release, exportar web/Android y desplegar --keep-vars. Esta última opción conserva también RFFM_SESSION. No incluir nunca las páginas autenticadas ni los registros privados en assets/offline/club.clubdata.
